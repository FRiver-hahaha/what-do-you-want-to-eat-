## 1. R21：回滚安全与同名表 fail-closed

### 1.1 问题

原草案回滚为裸 `DROP TABLE IF EXISTS`，存在三类风险：
1. 目标库若存在**同名但非本迁移创建**的表（他人手工建、旧版本建），裸 DROP 会误删他人数据；
2. 迁移中断后重跑时，若同名表已存在但结构不同，`IF NOT EXISTS` 会**静默跳过**，后续回填/查询在错误结构上执行；
3. 无法证明回滚删除的对象"仅限本次创建"。

### 1.2 修订方案（双重证据）

| 证据 | 实现 | 作用 |
|---|---|---|
| **S1 对象标记** | 4 张表 `TABLE_COMMENT`、`user.agent_uid` 的 `COLUMN_COMMENT` 统一以 `p8:migration=001_p8_business` 开头（表注释追加 `schema=p8-1;owner=backend-p8`） | 回滚前可判定"该对象是否本迁移创建"；无标记 → 拒绝删除 |
| **S2 manifest 文件** | 迁移 wrapper 输出 `migration_manifest_<UTC>.txt`：migration_id、目标库、实际创建/新增对象、种子 uid、自检结果 | 人工复核删除范围；SQL 无法读文件，由 wrapper 逐项比对后调用回滚 |

### 1.3 迁移前置判定矩阵（Step 0B，任一异常即非零退出）

| 现状 | 判定 | 动作 |
|---|---|---|
| 目标表不存在 | 正常 | 继续创建 |
| 存在且 COMMENT 含 `p8:migration=001_p8_business` | 本迁移遗留（断点续跑） | 继续（`IF NOT EXISTS` 不重建） |
| 存在但 COMMENT 无标记 | **来源不明** | **立即中止**，人工核查；禁止自动 DROP/重建/改结构 |
| `user.agent_uid` 已存在但 COMMENT 无标记 | **来源不明** | 同上（不自动改列、不自动加索引） |

> 明确禁止：任何情况下对来源不明的同名表执行 `DROP / TRUNCATE / RENAME / ALTER`。`DROP` 只出现在回滚脚本，且必须先过标记校验。

### 1.4 回滚脚本行为（`001_p8_business_rollback.draft.sql`）

1. 只读预检：四表 COMMENT、agent_uid 列 COMMENT、u_demo 行、user/friend 行数快照；
2. 存储过程 `p8_rollback_001` 内三项校验（表标记 / 列标记 / friend 表存在性），任一失败 `SIGNAL SQLSTATE '45000'` 中止，**校验全部通过后才执行 DROP**；
3. DROP 顺序：`idempotency_records → meal_records → health_profile → foods`（无外键，顺序仅为可读性）；
4. `agent_uid` 列：校验标记后 `ALTER TABLE user DROP INDEX uk_agent_uid, DROP COLUMN agent_uid`（`IF EXISTS` 判定，列已无则跳过）；
5. **不触碰** user（除该列）、friend 及任何旧表（message/file/group_info/group_user）；
6. u_demo 行默认**保留**（随机密码、不可登录），删除需人工显式执行并留证。

### 1.5 回滚后状态与重跑语义（如实说明）

| 项 | 回滚后 | 立即重跑迁移的结果 |
|---|---|---|
| 4 张业务表 | 不存在 | 重新创建（Step 0B 判"不存在"） |
| `user.agent_uid` | 不存在 | 重新加列 + 回填 |
| `u_demo@agent.local` 行 | **默认保留**（agent_uid 列为空） | Step 4 预检：`email_hit=1, same_hit=0` → **非零退出**（fail-closed，属预期保护） |
| 需要干净重跑 | 人工删除该行（先 SELECT 留证）后再跑 | 预检通过，正常创建 |

> 该"预检拦截"是 R16 的既定安全行为，不是缺陷；文档与运维检查单均要求"回滚后重跑前先处置 seed 行"。

## 3. R23：索引自检修正（7 → 8）与碰撞概率说明

### 3.1 修正内容

P8-S0 数据库迁移静态评审 §8 Step 7 原文："索引数 7（uk_agent_uid/idx_uid_date/uk_uid_key/idx_created_at/4 PK）"——**算术错误**（1+1+1+1+4=8）。本文件与 SQL 草案统一为 **8**，并已就地修正该评审文档（见 §5）。

### 3.2 索引逐项清单（自检必须四项全查：名称/所属表/唯一性/字段顺序）

| # | 表 | 索引名 | 唯一 | 字段顺序 |
|---|---|---|---|---|
| 1 | `user` | `uk_agent_uid` | 是 | (`agent_uid`) |
| 2 | `health_profile` | `PRIMARY` | 是 | (`agent_uid`) |
| 3 | `meal_records` | `PRIMARY` | 是 | (`id`) |
| 4 | `meal_records` | `idx_uid_date` | 否 | (`agent_uid`, `date`) |
| 5 | `idempotency_records` | `PRIMARY` | 是 | (`id`) |
| 6 | `idempotency_records` | `uk_uid_key` | 是 | (`agent_uid`, `idem_key`) |
| 7 | `idempotency_records` | `idx_created_at` | 否 | (`created_at`) |
| 8 | `foods` | `PRIMARY` | 是 | (`id`) |

补充断言（不计入 8）：既有 `user.PRIMARY(id)`、`user.email UNIQUE(email)` 必须仍存在且未被改写。

### 3.3 计数口径陷阱（必须写进自检实现）

`information_schema.STATISTICS` **每个索引按列拆行**：
- `idx_uid_date` 2 行、`uk_uid_key` 2 行、其余 6 个单列索引各 1 行 → **合计 10 行**；
- 因此 **不能**用 `SELECT COUNT(*) FROM STATISTICS` 断言 8（会得到 10 而误判失败）；
- 正确断言：`COUNT(DISTINCT CONCAT(TABLE_NAME,'.',INDEX_NAME)) = 8`（SQL 草案 Step 7.3 已实现）。

### 3.4 64 位哈希碰撞概率（生日悖论，补 §3 论证）

回填 uid = `legacy_` + SHA256(email#id) 前 16 hex = 64 bit（`2^64 ≈ 1.845×10^19` 空间）。
近似 `P(碰撞) ≈ n(n−1) / (2·2^64)`：

| 用户数 n | 碰撞概率（约） | 评价 |
|---|---|---|
| 1,000 | 2.7×10⁻¹⁴ | 可忽略 |
| 100,000 | 2.7×10⁻¹⁰ | 可忽略 |
| 1,000,000 | 2.7×10⁻⁸ | 可接受 |
| 10,000,000 | 2.7×10⁻⁶ | 可接受 |
| 100,000,000 | 2.7×10⁻⁴ | 需关注（远超本项目量级） |
| 5.06×10⁹ | ≈50% | 理论上限（`1.1774·√2^64`） |

结论：本项目演示/内部量级（≤10⁶）碰撞期望 2.7×10⁻⁸，且公式含 `id` 与 `email` 双重区分，实际碰撞还需 SHA256 前 16 hex 相同，**风险可忽略**。UNIQUE 索引为最终兜底：真发生碰撞 → 迁移报 1062 → fail-closed 人工处理（不静默覆盖）。
