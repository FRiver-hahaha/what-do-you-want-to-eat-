## 2. 三层真实架构（以代码为准）

```
浏览器 localStorage (app.js)                 ← 显示层与第二数据源
      │ fetch http://host:8787 (agent-adapter.js:2 BASE)
      ▼
Agent HTTP/SSE 层 (agent/server.py, ThreadingHTTPServer :8787)
      │ AgentApp.chat_events (app.py) → runtime → ToolContext (runtime.py:320)
      │ Tool handler → ServiceClient (data/service_client.py)
      │ urllib → EAT_SERVER_BASE_URL (默认注释示例 http://127.0.0.1:8080)
      ▼
C++ 服务端（P7 现状：仅 TCP:8000 + \n 分帧 JSON；HTTP 层待新建）
      │ MySQLPool / Redis
      ▼
MySQL（user/friend 两表） / Redis（offline_request）
```

关键事实：
- Agent 是 C++ 服务端的**唯一**调用方（前端从不直连 C++；app.js 的 fetch 全部指向 :8787，见 app.js:772/858/1075/1274）。
- Agent 自有 SQLite（agent/data/schema.sql 13 张表：sessions/messages/memories/market 系列/installed_skills/tool_audit/rag 系列/menu_imports/traces/spans）与 C++ 无关，归 Agent 管理。
- ServiceClient 未配置 EAT_SERVER_BASE_URL 时全部走 mock（service_client.py mode 属性）。
- Agent 请求 C++ 固定携带 `Authorization: Bearer {EAT_SERVER_TOKEN}` 与 `Content-Type: application/json; charset=utf-8`，超时 EAT_SERVICE_TIMEOUT（默认 5s），异常即回退 mock（service_client.py:_request）。

## 7. 结论

- C++ 需补齐的真实业务面 = ServiceClient 的 10 个 HTTP 接口 + **4 张 MySQL 新表 + user 表 1 列**（P8-07 口径）+ 评分/聚合计算。
- 前端与 Agent 均为零改动适配对象；所有兼容工作在 C++ 侧完成。
- 上游问题只记录（G-1..G-10），不改任何 Agent/前端代码；G-1/G-6/G-9 为阻断/待决策项（P8-12）。
