# P8-08 并发与线程模型设计（P8-2 修订版）

> 修订依据：R5 架构审查。本版严格区分**代码事实 / 理论估算 / 待实测项**，不把未测量数据写成已验证事实。

## 1. 代码事实（取证，非推测）

### 1.1 httplib 线程池（web/httplib.h:161-173 原文）

```cpp
#define CPPHTTPLIB_THREAD_POOL_COUNT                                            \
  ((std::max)(8u, std::thread::hardware_concurrency() > 0                        \
                      ? std::thread::hardware_concurrency() - 1                  \
                      : 0))
#define CPPHTTPLIB_THREAD_POOL_MAX_COUNT (CPPHTTPLIB_THREAD_POOL_COUNT * 4)
#define CPPHTTPLIB_THREAD_POOL_IDLE_TIMEOUT 3 // seconds
```

事实结论：
- 线程数 = `max(8, cores-1)`（**下限 8**），非"固定等于核数"（P8-1 表述修正）。
- **上限 = 基础数 ×4**（负载升高时可扩容），空闲 3s 回收。
- 因此并发 worker 数**不是常量**（8..4×(max(8,cores-1))）。例：8 核 → 基础 max(8,7)=8 → 峰值 4×8=32（**仅该硬件下的示例值，非通用上限，R17**）。

### 1.2 MySQLPool（server/database/MySQLPool.cc 原文）

```cpp
MYSQL* MySQLPool::borrow() {
    std::unique_lock<std::mutex> lock(m_mutex);
    m_cv.wait(lock, [this] { return !m_pool.empty(); });   // ← 无超时，无限等待
    ...
}
```
事实结论：
- **borrow() 无超时**（`m_cv.wait` 无 predicate 时限）；池耗尽时调用线程**永久阻塞**。
- init() 建 N 连接，任一失败 → 返回 false（无重试、无部分池可用性）。
- 无连接健康检查（ping/重连）——MySQL 重启后池中连接为失效句柄，借用即查询失败。

### 1.3 mysqlclient 线程约束（文档与版本要求，属外部事实）

- `mysql_library_init()` 必须在使用任何 MySQL API 前调用一次（进程级，非线程安全——须在创建线程前）。
- `mysql_init()/mysql_real_connect()` 创建的连接对象**不得被多线程同时使用**（独占使用即可跨线程转移）。本设计每 worker 独占借出连接，满足。
- **待实测项 M-1**：WSL Ubuntu mysqlclient 8.4 下"fork/线程 + 池化连接跨线程复用"的实际稳定性——S1 阶段以 8 线程压测验证并记录（不预设结论）。

## 2. 修订后的线程/连接模型

```
main 线程: mysql_library_init()（唯一、最优先）
          ↓
httplib worker（8..4×(cores-1) 动态，idle 3s 回收）
   每请求: 独占 borrow 一个连接 → 用完归还
          ↓
MySQLPool:
  size = S（CHATROOM_HTTP_DB_POOL；默认初始值 = W=max(8,cores-1)；实际值由配置决定并受全局连接预算约束，见 §2.1。**不存在通用固定 32 连接上限**）
  改造要求（S1 编码，本轮仅设计）:
    borrow_for(timeout_ms)  ← 新增，wait_for；超时返回 nullptr → internal_error(db busy)
    ping 复用前检查（mysql_ping，失效则重连 1 次，仍失败换连接/报错）
```

### 2.1 容量关系（R14 修订：配置决定，受全局连接预算约束）

- 基础 worker `W = max(8, cores-1)`（httplib.h 原文公式）；峰值 worker ≤ `4W`（动态扩容上限）。
- **DB pool 大小 S 由配置 `CHATROOM_HTTP_DB_POOL` 决定**（不由公式硬编码），其取值必须同时满足以下**全局连接预算**：
  1. MySQL `max_connections`（部署时 `SHOW VARIABLES LIKE 'max_connections'` 实测）；
  2. 既有 TCP 进程连接池（代码事实：8 连接，P7 既有）；
  3. 同机其他服务（Agent 不使用 MySQL；仍可能有运维/监控连接）；
  4. 运维连接预留（DBA 手工查询、备份等，建议 ≥5）。
- **默认档 S=W 作为初始配置**（演示/单机场景足够）；**高压档必须按实际预算计算**（S = min(4W, max_connections − 8 − 其他服务 − 预留)），**不得引用"4W≤32 永远安全"之类的通用结论**（P8-2 该表述废止）。
- **不承诺所有 worker 都能同时拿到连接**：峰值 4W 并发时等待是常态，borrow_for(3s) 有界等待 + `db busy` 错误是设计的一部分（配合 Agent mock 回退）。
- 容量数值（实际并发/实际连接数）在 S3 压测中记录，未测前不以任何公式承诺性能。

### 2.2 六层超时矩阵（R8 修订：逐层区分，禁止混称"SQL 超时"）

| # | 超时类型 | 值 | 作用对象 | 触发表象 | 能否终止在途 SQL |
|---|---|---|---|---|---|
| T1 | Agent urllib 超时 | 5s（EAT_SERVICE_TIMEOUT） | 客户端等待 | Agent 回退 mock | ❌（客户端放弃等待，服务端不知情） |
| T2 | httplib read/write timeout | 5s/5s | 连接读写 | 连接关闭 | ❌（handler 线程继续执行） |
| T3 | borrow_for 等待连接 | 3s | 线程等池 | `internal_error(db busy)` | ❌（尚未开始执行） |
| T4 | InnoDB 锁等待 | 3s（innodb_lock_wait_timeout） | 事务内行锁 | 事务报 1205 回滚 | ✅（唯一能中止 SQL 的机制，且仅限锁等待） |
| T5 | MySQL 网络读/写超时 | 可选 3s（MYSQL_OPT_READ/WRITE_TIMEOUT，S1 实测后定） | 客户端与服务器网络 | 连接失效（CR_SERVER_LOST） | ❌（服务器端语句可能仍在执行） |
| T6 | SQL 执行总超时 | **不存在** | — | — | — |

**结论：T1/T2/T3/T5 都不是"SQL 执行超时"，本设计不提供 SQL 执行取消能力（MySQL 客户端协议无语句取消，KILL QUERY 需独立连接）。**

### 2.3 在途事务与取消限制（R8 五问裁定）

| 问 | 裁定 |
|---|---|
| Q1 Agent 超时后 C++ SQL 是否仍可能继续执行？ | **是**。urllib 超时只是客户端放弃；服务端 handler 无感知，SQL 继续执行直至完成。 |
| Q2 客户端断开后服务端是否继续执行事务？ | **是**。httplib 仅在写响应时发现 EPIPE；事务按原逻辑提交/回滚。 |
| Q3 如何避免"用户看到 mock 但 MySQL 实际提交成功"？ | **无法完全避免**（无语句取消的必然结果）。三层缓解：① 幂等键（同一次重试→不重复写）；② 事务短小（两条 INSERT，毫秒级，超时窗口极小）；③ 下次读接口会呈现真实数据，mock 只影响当次响应且不缓存。**列为已声明风险（P8-13），不宣称已解决。** |
| Q4 连接超时/失效后如何避免错误归还复用？ | DAO 捕获 CR_SERVER_LOST/CR_SERVER_GONE/超时错误码 → **销毁该连接并重建（1 次）**，不归还池；归还统一走 `returnConnChecked(conn, healthy)`；borrow_for 命中后先 `mysql_ping`。 |
| Q5 如何验证超时后事务的真实提交/回滚？ | ① 制造慢事务（临时触发器 SLEEP(6) 或调试注入）→ 客户端 3s 断开；② 独立 mysql CLI 查 meal_records/idempotency_records 实际行数；③ 幂等重试同 key → 断言 receipt 一致且 1 行。用例 L3.36（P8-10）。 |

- 风险控制原则：**不追求取消，追求可判定与不重复**——事务原子性（两条 INSERT 同生共死）+ 幂等键 + 事后核查。

## 4. MySQL 故障恢复（本次补充，R5 必答项）

| 场景 | 现状（代码事实） | 设计处置（S1 编码） |
|---|---|---|
| MySQL 重启 | 池内连接全部失效，借用后查询报 CR_SERVER_LOST | ① 启动自检（/health db:false 不阻塞启动）；② 借用前 mysql_ping，失效则重建该连接（1 次重试）；③ 重建失败 → internal_error(db unavailable) |
| MySQL 长时间宕机 | 池空 + 无限等待（原实现） | borrow_for 3s 超时 → db unavailable；每 worker 不悬挂 |
| 恢复后 | 手动重启进程才恢复（原实现） | ping 重建使连接自愈；无需重启进程（S1 验收项） |
| 降级语义 | — | C++ 返回 internal_error（2xx 体）；**Agent 若连接级失败/超时→mock 回退，用户看到演示数据**——降级链如实写入 KNOWN-ISSUES |

## 5. 关闭语义（本次补充，R5 必答项）

```
SIGTERM → httplib::Server::stop()（停止 accept，等待当前请求写回）
        → 请求处理完毕（上限 5s：读写超时保证有界）
        → server 对象析构 → MySQLPool 析构（逐连接 mysql_close）
        → 进程退出
```
- 在途请求处理：httplib stop() 默认等待活跃请求（S1 实测确认其行为与版本一致；不等则加 5s 宽限 + 强制退出——**待实测项 M-2**）。
- 事务中断（进程被 kill -9）：单事务两条 INSERT 未提交 → InnoDB 回滚 → 无孤立记录（P8-06 §4.2 断言覆盖）。
- **不做优雅 draining 的负载均衡语义**（单进程部署，重启即短暂不可用，Agent 有 mock 回退）。

## 6. 并发正确性（与 R2 对齐）

- 幂等并发：唯一键阻塞串行化（P8-06 §4.2 时序图），先 meal 后 idem + 冲突回滚 → 无孤立行。
- PATCH profile：UPSERT 行锁。
- foods 只读内存缓存（启动加载，无需失效）。
- 无跨请求共享可变状态（除池与只读缓存）。

## 7. 与现有 TCP 进程的关系（不变）

server(TCP:8000) 零改动；两进程各自 MySQLPool 实例；连接数 = HTTP W/S + TCP 池（TCP 8 连接，代码事实）→ 总 <151。
