# P8-05 身份认证与用户映射设计（P8-2 修订版）

> 修订依据：R1 架构审查。本版**不回避**身份链断裂问题，如实标注阻断项。

## 1. 现状事实（代码取证）

### 1.1 TCP 注册/登录产生的用户身份（P7 代码，ChatService.cc）

| 流程 | 输入 | 行为 | 产出身份 | agent_uid |
|---|---|---|---|---|
| 注册 signUp | email+name+password+验证码 | 验码→SHA256(密码)→INSERT user | `user.id`（int，自增）；email UNIQUE | **不生成**（INSERT 不含该列） |
| 密码登录 signIn | email+password | 查 email→比对哈希→`tryLogin` CAS 置 state=1 | 会话绑定 `conn->setUserId(id)`；返回 id/name/email | 不涉及 |
| 登出/注销 | 会话 | state=0 / 级联删 friend+user | — | — |

结论：**真实注册体系的主键是 email（唯一锚点），运行时身份是 user.id（int）。**

### 1.2 Agent 侧 user_id 的真实来源

| 环节 | 取证 |
|---|---|
| 前端 | `state.userId = localStorage.getItem("eat-agent-user") || "u_demo"`（agent-adapter.js:33）——任意字符串，用户可改 |
| 传输 | 每次 `POST /api/chat/stream` body.user_id（agent-adapter.js:942） |
| Agent | `request.setdefault("user_id", DEFAULT_USER_ID)`（app.py:153）→ ToolContext.user_id → 拼进 ServiceClient URL |
| C++ | 原设计仅做格式+存在性校验 |

### 1.3 判定：两条身份链**互不相通**

- TCP 的 email/密码/验证码从未进入 Agent 链路；Agent 的 `u_demo` 从未与任何 `user` 行绑定。
- 前端**不存在**登录界面（localStorage 键可任意编辑，无鉴权 UI），因此没有任何"当前用户"的可信声明到达 C++。
- **Bearer Token 只证明"调用来自持有 Token 的 Agent 进程"，不证明"当前是哪个自然人"。**

## 2. 攻击面分析（零改动约束下能防什么、防不住什么）

| 攻击 | 零改动下结果 | 依据 |
|---|---|---|
| A1 改 localStorage `eat-agent-user` 为他人 uid | **可越权读写该 uid 全部数据**（若猜中 uid） | Token 由 Agent 持有，C++ 视一切 uid 合法；无用户会话凭证 |
| A2 枚举 uid（u_demo / u_lin / 短名） | **可探测存在性**（user_not_found vs 200）并通过读接口拉数据 | 读接口无速率限制、无用户凭证 |
| A3 写路径 lazy 建户 → 无限造户/污染排行 | 原设计**允许**（本版取消，见 §3-C） | 原 P8-05 §3 lazy provisioning |
| A4 直连 8080 伪造请求 | 需同时持有 Token；若 8080 暴露公网且 Token 泄露 → 全数据可读写 | Token 为唯一防线 |

## 3. 零改动约束下的缓解（缩小面，但不能根治）

**A. Token 强化（保留）**：常数时间比较；fail-closed；8080 仅绑定 127.0.0.1；Token 随机 ≥32 字节；定期轮换。

**B. uid 校验强化（保留，R15 统一格式）**：路由与 Auth 统一使用 `[A-Za-z0-9_-]{1,64}`（**允许连字符**，连字符置于字符类末尾避免转义歧义）；Router 与 Auth 双处校验，**任何路径解析失败一律 invalid_params 直接返回，不进入 UserDao 及任何 Controller**；读路径要求 uid 已存在（不存在→user_not_found）。

**C. 取消写路径 lazy 建户（本版修订）**：
- 原设计（P8-1）允许未知 uid 经 PATCH/POST 自动建户——攻击者可无限注册 uid、污染 ranking/foods 统计。
- 修订：**写路径同样要求 uid 已存在**（不存在→user_not_found）；仅 `u_demo` 由迁移 seed 提供；其他 uid 必须由"注册流程 + 桥接机制"产生（桥接见 §5，未实现则为阻断）。
- 后果（如实）：多用户场景下，除非走 §5 桥接，**除 u_demo 外的任何 uid 都无法写入**——产品当前是单演示用户形态。这是安全与可用性的现实取舍，写入 P8-12 阻断项。


**C2. P4 模式：服务端强制单用户隔离（R6 修订，唯一有效防线）**：
- 环境变量 `CHATROOM_HTTP_USER_MODE`，**fail-closed 启动自检（R11）**：
  - `p4_demo`（默认）：正常启动，Auth 只允许 `uid == "u_demo"`；
  - `multi`：**当前未实现 → 启动时 FATAL 退出**（`LOG(FATAL) << "user_mode=multi not implemented"`），不得以"半成品多用户"姿态运行；
  - 未知配置值（空/拼写错误/其他）：**启动 FATAL 退出**；
  - **禁止** multi 模式以任何形式"退回 UID 存在性校验"——multi 正式实现时必须是 Token→uid 绑定（P1/P2），存在性校验永远只是辅助。
- **校验顺序固定（R11）**：Router 正则 → Auth Token → **p4_demo 白名单（先于 UserDao）** → UserDao/Controller。白名单是 Auth 内第一业务判定，先于一切数据访问。
- **p4_demo 模式 Auth 硬编码判定：`uid == "u_demo"` 才放行；其余一切 uid（含数据库中真实存在的 legacy_*、注册用户、任意字符串）一律 `{ok:false,error:"forbidden",message:"single-demo-user mode"}`。**
- 该判定**不查库、不看前端**：不是隐藏入口、不是文档声明，而是服务端常量比较（Auth 层，先于所有 Controller）。
- u_demo 仍需 Bearer Token（服务身份）——两层叠加：Token 证明调用方是 Agent，白名单证明访问对象只能是演示户。
- **P4 是演示隔离，不是多用户认证方案**：它把"改 user_id 越权"收敛为"任何非 u_demo 访问直接拒绝"，代价是产品无多用户能力。若选 P1/P2，则整段替换为用户 Token 绑定（`multi` 模式），**不得两种安全模型混用**（单次部署只能选一种）。

**C3. legacy_* 回填在 P4 模式下的定位**：回填仅为数据完整性/未来迁移保留；P4 模式下这些 uid **不可访问**（被 C2 白名单拒绝）。

**D. 响应差异最小化（保留）**：错误 message 不回显 uid 之外的信息；日志只记 uid 与来源 IP。

**E. 限流（可选，实施阶段评估）**：按 IP+uid 的读接口每分钟限额（Redis 或进程内令牌桶）——非本轮设计必需，列为 S1 可选项。

## 4. 跨用户访问攻击测试用例（P8-10 L2 必须实现）

> 这些用例在零改动约束下的**预期结果是"攻击可复现"**——它们的作用是**证明阻断项真实存在**，而非验证防护成功。任何人不得把这些用例标为 PASS 宣称安全已解决。

| 用例 | 步骤 | 零改动下的预期（断言口径） |
|---|---|---|
| ATK-1 | 前端 localStorage 将 `eat-agent-user` 设为 `u_victim`（先由迁移 seed 建该 uid 并写 1 条 meal）→ 发起 chat "看看我的饮食记录" | Agent 工具以 u_victim 调用 C++ → **返回受害者数据**。断言：响应 meals 含受害者记录 ⇒ 越权成立（BLK-1 复现，标记 XFAIL/REPRO） |
| ATK-2 | 直接 HTTP：`GET /api/v1/users/u_victim/health-profile` 带正确 Token | 200 + 受害者档案 ⇒ 无障碍读取（BLK-1 复现） |
| ATK-3 | 无 Token 请求 | `{ok:false,error:"unauthorized"}` ⇒ 防护有效（PASS） |
| ATK-4 | 错误 Token | 同上 ⇒ PASS |
| ATK-5 | uid=`../etc`、`u demo`、65 字符 | `invalid_params` ⇒ PASS（格式防线） |
| ATK-6 | uid=`u_unknown`（不存在）读 | `user_not_found` ⇒ PASS（存在性防线） |
| ATK-7 | uid=`u_unknown` 写（PATCH profile） | `user_not_found` ⇒ PASS（本版取消 lazy 后的行为） |
| ATK-8 | Token 泄露后直连 8080（**p4_demo 与 multi 均适用**） | **仍可操作 u_demo 数据 ⇒ REPRO**（Token 是服务身份，白名单只限制「访问哪个 uid」，不阻止「以合法 Token 访问 u_demo」——R12 统一口径，**任何文档不得把 ATK-8 写成 PASS**） |
| ATK-9（P4 模式） | `GET/PATCH /api/v1/users/legacy_xxx/...`（库中真实存在） | `{ok:false,error:"forbidden"}` ⇒ PASS（R6 白名单） |
| ATK-10（P4 模式） | 任意非 u_demo uid（含注册用户 u_lin） | `forbidden` ⇒ PASS |
| ATK-11（P4 模式） | `u_demo` 读写 | 正常 200 ⇒ PASS（正向可用性） |

**测试结论模板（R12 统一口径，按部署模式）**：
- **p4_demo**：ATK-1/2 = **PASS**（其他 uid 被白名单拒绝）；ATK-3~7 = PASS；ATK-9/10 = PASS（legacy_*/任意 uid → forbidden）；ATK-11 = PASS（u_demo 正常）；**ATK-8 = REPRO（Token 泄露仍可操作 u_demo——白名单不解决 Token 保管问题）**。
- **multi**：ATK-1/2 = REPRO（若身份绑定未真正实现）；ATK-8 = REPRO。
- P8-10 报告必须按部署模式分别呈现；**ATK-8 在任何模式下都不得记为 PASS**。

## 5. 根治方案（需学长决策，超出零改动约束）

| 方案 | 机制 | 需改动的上游 |
|---|---|---|
| P1 用户会话 Token（推荐） | 前端接入登录（复用 TCP signIn 或 Agent 代理登录）→ 服务端签发用户级 JWT/随机 token → Agent 透传 `X-User-Token` → C++ 校验 token→uid 绑定 | 前端加登录 UI + Agent 加身份透传（两处改动） |
| P2 Agent 可信声明 | Agent 内部维护 用户会话↔uid 映射（例如以 chat session 首次声明绑定），C++ 采信 Agent 的签名声明 | Agent 改动 + 双方共享签名密钥 |
| P3 TCP 账号与 uid 桥接（最小） | TCP 注册成功后返回 agent_uid（=确定性哈希），由用户手动在前端"账号设置"填入 localStorage | 前端加输入框（1 处小改）+ TCP 注册响应加字段（C++ 自改，允许） |
| P4 维持单演示用户 | 明确产品边界=单机演示，u_demo 独占；禁止多用户 | **C++ Auth 层新增服务端白名单，强制 uid == u_demo；非 u_demo 一律 forbidden；前端与 Agent 不需要修改**（与 §3-C2 一致，R20） |

## 6. 本版最终口径

| 问题 | 回答 |
|---|---|
| 1. TCP 注册登录如何产生身份？ | email 唯一锚点 + int id；§1.1 |
| 2. Agent user_id 如何与注册用户关联？ | **当前无关联**（代码取证：注册不含 agent_uid；前端无登录） |
| 3. 如何防止改 user_id 越权？ | **P4 模式**：服务端白名单使非 u_demo 一律 forbidden（ATK-1/2 PASS）；**multi**：无法真正防止（ATK-1/2 复现）。注意：P4 不阻止 Token 持有者操作 u_demo（ATK-8 仍 REPRO） |
| 4. 是否需要 Agent 可信身份声明？ | **是**，为唯一根治路径；§5 P1/P2 |
| 5. 是否阻断？ | **是：BLK-1 用户身份不可信（安全阻断）**，未解决，见 P8-12 |

## 7. u_demo 与 name 的裁定（其他一致性 #6/#7）

- `user.name`（账号昵称）与 `health_profile.name`（健康称呼）是**两个概念**：profile 首次创建时默认取 user.name，之后独立可改，不做双向同步（避免改称呼诱发账号昵称变化）。
- 注册产生的 user **不写 agent_uid**（保持 P7 行为不变）；迁移仅对存量行做确定性回填：**`legacy_` + `SHA256(email + '#' + id)` 前 16 位**（**以 P8-07 §2.1 实际 SQL 为唯一口径，R18**），不与 Agent 的任意 user_id 建立绑定（无法建立）。
